# 8.3.6防甩机制（AP 取消重请求协调器）实车验证规程（两级，2026-09-14，适配 v4.5.0-beta14）

## 决定与前提

**v4.5.0-beta03 起，AP 注入门控是 8.3.6防甩机制的运行前提**（2026-09-11 Jordan
定义的整体框架）：

- **门控关 = 机制完全静默**：不触发轮次、不发送 0x045、不拦截任何注入——
  Legacy 走原始直通路径，这是**非 8.3.6 车型的正常设计模式**（用强制激活即可，
  不会甩）；
- 门控关时「8.3.6防甩机制」开关**仍可拨动**（记住你的选择，状态行显示
  「不可用 · AP 门控未开启」），门控重新打开后**自动恢复武装**，无需重拨开关；
- 门控开 + 开关开 = 协调器成为唯一激活权威（本规程要验证的模式）。

用户决定**跳过独立台架，直接实车验证**。本规程把风险拆成两级：

- **Tier 0（停车检查，~10 分钟，零行驶风险）**：上车前把配置、武装状态、
  拨杆标定检测器、录制器全部确认一遍。独立台架能查的（TX 组帧、counter/
  CRC、状态机），停车实际上查不到——协调器按设计**只在 AP 激活边沿**才
  开始一轮（`exitSeen + intent + 未激活→激活`，AP∈[3,6] 边沿），停车时
  AP 不会激活，所以**停车阶段设备不会发送任何 0x045**。Tier 0 能查的是
  其余一切；TX 链路只能在 Tier 1 验。
- **Tier 1（受控低速首轮）**：真实 AP 激活边沿，协调器第一次在真实总线
  上跑完整轮。必须封闭/空旷场地 + 低速 + 全程手扶方向盘。

## 触发机制速览（先懂这个再上车）

| 事实 | 含义 |
|---|---|
| 一轮只在 **AP 激活边沿**触发（武装中 + intent 在 + 见过完整退出） | 开着开关正常激活 AP（拨杆或车机均可）就触发，无需额外操作 |
| **握手术中碰物理拨杆 → 本轮锁死**（reason=`physicalInput`） | 一轮约 2-3 秒，期间手扶方向盘但**别碰拨杆** |
| **车辆侧异常（窗口过期/AP 退出/AP 自恢复/故障态，beta14 起再加请求被拒/取消被无视）→ 自动重武装**，连续 3 次后才真锁死（`autoRearmLimit`） | 大多数异常**无需任何开关操作**，正常重新激活 AP 即开下一轮 |
| 硬件类锁死（计数器冲突/发送失败等）→ **开关关→开** 重新武装 | 排查/复测的标准动作 |
| 一轮的体感：AP 激活 → 自己取消（约 0.2-0.5s）→ **静默等车回可用态（约 1-1.5s，此间 AP 保持关闭）**→ 自己重新请求恢复（约 0.2-0.5s）| **这是设计行为，不是车辆故障**；不恢复=AP 保持关闭（安全态）。**beta14 起**：重请求被拒会静默再等 ~1s 自动重发（每轮 ≤2 次）；取消被无视 ~0.7s 会自动重发一次取消——体感可能出现「取消-等待-再取消」或等待比往常长 1-2s，同样是设计行为 |
| 测完开关关 = 完全回到旧行为 | 随时可用开关终止实验 |

## P0 故障取证规程（beta10 新增：再遇「无法注入」时严格照此顺序）

beta08 实车三症状里最贵的一类证据损失：症状 2/3（强退 FSD 后 / 长时间
运行后注入失效，开关循环无效，仅拔插恢复）的挂死态在 RAM 里，**拔电 =
销毁证据**。beta10 的观测层 + NVS 黑匣子就是为这个场景而生。再遇到
「无法注入」时：

1. **先取证，别动任何东西**：立刻截图 `/status`（或
   `curl -s <IP>/status > 故障时刻.json`）+ `/defense_config`。重点看：
   - 「许可链」格是否「正常」，断的话断在哪个输入（总开关/处理器/
     驱动/OTA守卫/AbortGuard）；
   - 「心跳」格是否「活跃」还是「停滞 Ns」（停滞 = tick 饿死）；
   - `permitInputs` / `permitBits` / `tickHeartbeat` / `otaWatch`
     （尤其 `otaGuardClear=false` + `otaWatch.active=true` +
     `last318Ms` 长时间不涨 = OTA 守卫卡死实锤——头号嫌疑；
     beta12 起 `blockedMs` 直接给出已封锁时长，`staleClears>0` 说明
     停流降级已自动救过场）；
   - `blackbox` 最后几条（permitChange/intentChange/lock）。
2. **再试开关循环**（8.3.6 开关 关→开）：预期对症状 2/3 无效（这正是
   beta08 的实车反馈），但无效本身也是证据——记录。
3. **仍无效才拔电重插**。重插后**第一件事**（操作任何开关之前）：
   再取一次 `/status`——blackbox 里**最新的 `boot` 条目之前**的那些条目
   就是断电前最后的证据（permitBits 位图直接指出断的输入）。
   **注意**：wedge 期间 Web UI 可能也完全不可达（若整机挂死）——这正是
   黑匣子跨断电存活的意义：重插后第一次 `/status` 依然能看到死前记录。

**判读速查（beta10 观测字段）**：

| 观察 | 结论 | 下一步 |
|---|---|---|
| `permitInputs.otaGuardClear=false` + `otaWatch.active=true` + `last318Ms` 不涨 + `blockedMs` 持续增长 | **OTA 守卫封锁中**（置位后 0x318 停发）；beta12 起 **10 分钟后自动降级解除**（`staleClears` +1 + 日志 `[OTA] guard stale-clear`），不再是永久卡死 | 等 10 分钟看是否自愈并记录 `staleClears` 变化；若确认为真 OTA 应保持封锁——需要临时继续注入时用「忽略车辆 OTA 守卫」开关（诊断用途，真 OTA 进行中有风险） |
| `otaWatch.staleClears>0` | 停流超时降级**已发生过**（守卫自己救了场） | 发回 JSON；结合 `blockedMs` 与日志确认发生时刻 |
| `otaWatch.override=true` | 用户覆盖开关开着（守卫被忽略） | 确认为有意开启；排查完记得关（关闭后真 OTA 仍会被 3 帧重新捕获） |
| 两次 `/status` 间 `tickHeartbeat.count` 不涨（「心跳」格停滞） | CAN 任务层饿死（tick 挂死） | 发回；P2 方向 = permit 卡死自愈 watchdog |
| `txAccounting.consecutiveFails` 持续增长 / `fails` 增长而 `ok` 不动 | 注入发送本身在失败（总线侧挂起，症状 3 类） | 发回；对照 TWAI/MCP2515 诊断（TEC/REC/bus-off、SPI 错误） |
| `carrier3ee.longGaps` 增长 / `maxGapMs` 常态 ≳2000 | 资格窗内载波节奏问题（症状 1「只出现 EAP」的方向性证据：窗内 mux0 载波静默） | 发回 + 结合 CSV 的 0x3EE 时间轴分析 |
| `permitInputs.canActive=false` | CAN 驱动退化（UI 上 CAN 状态也可见） | 发回；对照 TWAI 诊断（TEC/REC/bus-off） |
| blackbox 断电前最后一条 `permitChange` 且 `permitBits` bit3=0 | 断电前 OTA 守卫输入已断 | 与 otaWatch 互相印证后发回 |
| blackbox 断电前最后一条 `lock`（reason=counterConflict 等） | 协调器**内**锁死（另一类问题，开关循环本应可解） | 若开关循环确实无效则矛盾——更说明 wedge 在外层，发回 |
| 全部正常但注入仍失败 | permit 五输入之外的原因（intent 链/资格窗内载波） | 结合 round 诊断 + `carrier3ee` + CSV 分析 |



1. **刷机**：WebUI OTA 上传 `LILYGO-T-2CAN_v4.5.0-beta14_ota_app.bin`；重启后
   /status 版本 = **4.5.0-beta14**，**先 `curl -s <IP>/status | python3 -m
   json.tool` 或页面确认 JSON 可解析**（beta07 教训的烧后一步验证），
   FSD 防护页从上到下依次为
   **「FSD 防护总开关」→「AP 注入门控/自动恢复」两卡（beta06 起无延迟选项）→
   「8.3.6防甩机制」**开关，卡片描述显示"编码/时序已按 2026-09-10/11 实车抓包标定"。
   刷完顺手验证观测层：`/status` 内 `permitInputs`/`tickHeartbeat`/`otaWatch`
   （含 beta12 新键 `staleClears`/`override`/`blockedMs`）/
   `blackbox`/`carrier3ee`/`txAccounting` 六组键在、`apReRequest` 内 beta14
   新键 `counterSkips`/`cancelRetries`/`requestRetries` 存在且为 0、blackbox 首条为 `boot`
   （seq=1）、诊断网格「许可链」
   显示「正常」、「心跳」显示「活跃」；FSD 防护页有「忽略车辆 OTA 守卫」

2. **开录制器** 120 秒，过滤 `45,399,3EE,488`（全程不关；488 = 转向扭矩，

3. **确认上方「AP 注入门控」开关已打开**，再打开"8.3.6防甩机制"开关，
   立即看诊断（`/status` 或
   `/defense_config` → `legacyInjectionSafety.apReRequest`）：

4. **拨真实拨杆**：前推一次、后拨一次（停车，车不会有反应）。

5. **门控 关→开 验证（beta03 新前提，录制不关）**：关掉「AP 注入门控」→

## Tier 1：受控低速首轮

**场地要求**：封闭/空旷、**有车道线**（无标线的空停车场 AP 可能到不了
激活态，验证不到资格段）、低速（AP 最低激活速度之上即可，越低越好）。

**准备**：录制器开 120s；诊断页在手机上可见；开关确认 armed
（reason=waitApActive）。**AP 注入门控必须开**——新框架下门控关=机制
不运行（Tier 1 会白跑）；「8.3.6防甩机制」开关也必须开。

**每轮动作**：正常激活 AP（拨杆或车机）。然后**只观察，不操作**：

1. AP 激活后约 0.2-0.5s → 设备合成取消 → AP 掉（0x399 → 状态 1）；
2. **静默等待约 1-1.5s**（beta04 新时序：设备等 0x399 回状态 2=可用，
   诊断 reason=`waitAvailable`，此间设备零发送、AP 保持关闭）；
3. 车回可用态后 → 设备合成重请求 → AP 恢复（2→3 约 0.2s，加载波窗口
   最长 2.4s）→ bit46 注入；
4. **观察这一次最终激活的方向盘体感**（这就是假设要回答的问题）；
5. **观察激活保持时长**（beta05 新增观察项）：beta04 轮 1 形态 = FSD 3→6
   激活后 ~250ms 车自掉（无甩动、无拨杆、无 8/9）。每轮记录：激活是否
   保持、若掉线距注入多久——这正是 488 录制要鉴别的问题，多轮数据
   才能区分"单帧断言不足"与其它原因。

双手不离方向盘。任何时候：物理拨杆或刹车=立即取消 AP（若正处于握手术
中则本轮同时锁死——正常，开关关→开再测）。

**每轮结束记录**：诊断里的 `reason` / 轮次计数器 / **上次结束原因** /
**自动重武装**计数（beta06 新增，跨开关操作保留）/ 下载或标注 CSV 时段。
**仍建议先记 reason 再做任何开关操作**——beta06 的 `lastEndedReason` 已跨
重武装与状态变化保留（beta05 Tier 1 教训的直接修复），但截图留档永远最稳。
建议 3-5 轮。

**出错后的恢复动作（beta06 起大幅简化）**：
- **车辆侧异常无需任何操作**：窗口过期 / AP 退出 / AP 自恢复 / 故障态
  （状态行带"·已自动重武装"后缀）设备已自动回到武装态——正常重新激活
  AP（完整退出后）即开下一轮，**不用碰任何开关**；
- **连续 3 次车辆侧异常**（状态行 `autoRearmLimit`·锁定）→ 把
  「8.3.6防甩机制」开关 关→开 重置预算；连续 3 次说明车辆持续不配合，
  重置前先把 CSV 发回分析；
- **硬件类锁死**（计数器冲突/发送失败/许可丢失/物理拨杆/超时等，状态行
  带"·锁定"后缀）→ 同样开关 关→开；**不需要动 AP 门控**；
- **不要用关门控来恢复**：门控关 + 强制激活开着 = 旧直通路径立即恢复 bit46
  自由注入（beta05 三段 CSV 中的延迟注入群就是这些窗口的旧路径帧；好在
  当时 AP 未激活车没理会——若恰在激活边沿，防甩前提就没了）；
- 记住锁死期间的语义：开关开 + 锁死 = 设备**暂停一切** FSD 激活注入
  （此时按强制激活不会有反应，是设计行为不是设备坏了）——先看状态行的
  中文 reason，再决定重武装还是停测。

## 方案 A：原生激活对照鉴别测试（甩幅归因，2026-09-12 新增）

**要回答的问题**：两份 Tier 1 CSV 已定位甩动时序=state6 后 186-330ms
固定相位的**车固有 FSD 初始车道捕捉**（R3 出现过 42.6° trackAngle
三拍摆动≈第一份 CSV 最大值的 11 倍）。但**协调器的取消→重请求打断
是否放大了这一捕捉**仍无法排除——4 轮注入帧字节逐字节相同而摆幅
1.1-42.6° 不等，说明内容无关，但打断-放大的可能仍在。本测试用
**旧直通路径的原生激活**（无打断、无取消重请求）作对照组。

**⚠️ 本测试故意重现历史猛甩路径**（关门控 + 强制激活开 = bit46 从
CAN 活跃起常注，即 8.3.6 之前的旧路径）。只在封闭场地、低速、双手
全程不离方向盘时做；任何异常体感立即 FWD 取消。

**设置**（与 Tier 1 完全相反的一组开关）：

1. 「8.3.6防甩机制」开关**关**（门控关时它本就不运行，关掉更干净）；
2. 「AP 注入门控」**关**——此时 Legacy 直通路径合法接管（beta03 框架
   的正常设计模式）；
3. 强制激活（force）**开**——bit46 注入的唯一 intent 来源；
4. 录制器开 120s，过滤 **`45,399,3EE,488` 不变**。

**每轮动作**：低速行驶中**原生 RWD 拨杆激活 FSD**（设备不干预——无
取消、无重请求、无打断，bit46 从 CAN 活跃起持续注入）。观察初始车道
捕捉体感。3-5 轮。随时 FWD 取消。

**对照组**：已有 9 个协调器轮次（143736 CSV 4 轮 + 162535 CSV 5 轮），
无需重录。

**分析方法**（CSV 发回后由 Claude 做）：对每轮取 state→6 后 186-330ms
固定相位窗内 0x488 trackAngle（b0b1 大端 −16384，×0.1°，仅 type=2 帧）
的最大单拍 |Δangle| 与总摆幅，两组对比：

- 原生组摆幅 ≈ 协调器组（同量级分布）→ **打断不放大**，甩=车固有
  （初始车道捕捉），协调器无责，防甩假设不受损；
- 原生组明显更小（如全部 <5° 而协调器组屡现 >10°）→ **打断放大实锤**
  → 启动方案 D（重请求等待自适应，先设计后报批，不直接改代码）。

**做完立即恢复**：门控重新打开（8.3.6 防甩机制随之恢复武装）。注意
关门控期间是历史猛甩路径在跑——测试窗口之外不要保持此开关组合。

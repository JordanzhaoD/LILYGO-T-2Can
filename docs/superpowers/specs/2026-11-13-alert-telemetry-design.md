# 告警遥测产品化设计（Alert Telemetry / 降级日取证仪器）

> 状态：待 Jordan 批准 · 2026-11-13 · 分支基线：ban-shield-x（beta15+grid-fix 56206ef 之后）
> 课题背景：`Atlas-3CAN-P4/docs/ban-shield-0x368-forge-experiment-design-20261111.md` §13/§14（Stage B 告警指纹 + 开机窗终局）

## 1. 意图与为什么

**降级真发生的那一天，这台设备必须已经替你完成了取证。**

三个上游事实决定了本产品：

1. **告警三连已全命名**（Stage B 双实验）：巡航禁用=a124、动力下降=a062（b7bit5≈w062 systemLimpMode）、需检修=a144 整车配置告警；执法者=驱动逆变器 DI/DIS（0x526/0x5A5），PM（0x524）未触发。
2. **告警通道零误报体质**：0x526/0x5A5/0x524 事件驱动、正常驾驶全程零帧；0x346 矩阵空闲全零。无需去抖/过滤/调参。
3. **PM_a043 是"写回路线"的直接探针**：`PM_a043_configInconsistent` 携带 `GTW_autopilot vs expectedAutopilot` 显式对。降级日它开口=期望值更新滞后于镜像=存在竞态窗口→inline 改写可行且能吞掉原生告警；全程静默=期望值被原子同步→inline 改写会炸告警。**本产品是决定"要不要做写回工程"的仪器。**

配合已实现的 0x368 tripwire（ban-shield-x），构成降级监控完整闭环：tripwire 报"档位镜像变了"，告警遥测报"车怎么反应的、为什么"。

## 2. 目标 / 非目标 / 反目标

**目标**
- 五源哨兵常驻被动监听（纯 RAM，零 TX，零常驻闪存写）：tripwire(0x368 偏离)、0x346 矩阵置位、0x526/0x5A5/0x524 日志帧
- 事件即取证：自动抓拍（pre 上下文来自监听集 PSRAM 环回灌 + post 上下文来自黑盒自动开闸锁定）
- 事件持久化到 NVS（掉电幸存），WebUI 防护页可读、可导出
- 0x346 位图与 DI/DIS/PM a-码静态解码表（w/a 码空间同源，一张表服务矩阵与日志）

**非目标**
- 推送通知（设备无外网推送通道；WebUI 局域网可见即止）
- 全告警矩阵家族覆盖（0x329/0x5B9/APP 矩阵等——后续课题，架构上只是加监听 ID）
- 写回/恢复配置（inline 串接是独立硬件工程，本产品只产出决策证据）
- 监听 ID 集的用户可配置性（硬编码+代码表，简约优先）

**反目标（做了即失败）**
- 任何形式的总线发送（本产品纯只听；与 forge 的 TX 纪律同源）
- 常驻闪存写（违背 beta13 闪烁案终局：全速率串流与无缝注入互斥）
- 告警风暴撑爆存储或占死黑盒保护块（自动清理必须有界）

## 3. 约束（继承自项目纪律）

- fail-closed：偏好默认关/开都要有明确语义；异常路径不得留半开状态
- NVS 键 ≤15 字符（超限静默拒写——坑在案）
- 黑盒保护块占满=写者拒写（refuse-when-full）→ 自动抓拍会话必须自清理
- 哨兵热路径在 CanC 帧派发处（`mcp2515_dashboard.h` ban forge 块同层），每帧预算极小（查表+位比较）
- 板 2 供电形态（车 USB 深睡断电/充电宝）下事件日志必须掉电幸存 → NVS 而非 RAM
- 纯核心头文件模式（`dash_ban_forge.h` 先例）：无堆、无 Serial、无 Arduino 调用；inline 联结（双 TU 引用不分叉）

## 4. 方案裁决记录（对话已定）

- **A 哨兵+自动抓拍（采纳）**：常驻 RAM 哨兵 → 事件触发黑盒开闸+锁定+关闸；pre 上下文由监听集 PSRAM 环回灌
- **B 纯哨兵（否决）**：无总线上下文，取证价值砍半
- **C 串流常开（不提供）**：直接违背 beta13 闪烁终局

**pre 上下文载体的子决策**（我的裁定，可改）：监听集 PSRAM 环（~14 ID 过滤，256KB）而非全量环（2-4MB）。理由：因果链全在监听集内（镜像+矩阵+日志+Stage B 指纹族+0x3EE/0x398 锚）；回灌量小（~1-2s 闪存突发，闪烁窗可忽略）；全量 pre 保真由"事件后黑盒常开段"补足。256KB×18B 帧 ≈ 4 分钟监听集历史，远超需要。

## 5. 架构

### 5.1 纯核心 `include/dash_alert_watch.h`（新，仿 dash_ban_forge.h）

```
状态：g_alertWatchPref（总开关）、监听集命中环（PSRAM, 256KB）、
     事件环形日志（RAM 镜像 + NVS 持久，24 条）、抓拍状态机、解码表
入口：dashAlertWatchOnFrame(id, dlc, data, nowMs)   ← CanC 派发块调用
     dashAlertWatchPoll(nowMs)                       ← loop/web 任务异步驱动抓拍
出口：dashAlertWatchDiag()（状态 JSON 源）
     dashAlertWatchDrainRing(cb)                     ← 回灌迭代器
```

**哨兵语义**：
- `0x368`：复用 ban forge tripwire 的命中信号（不重复实现；事件源=该计数器增量）
- `0x346`：64 位中任一 0→1 上升沿=事件（码=位号 w001-w064）；下电前不清零的语义照车（我们只记上升沿）
- `0x526/0x5A5/0x524`：任一帧=事件（码=b0=aXXX；a043 特解：标记"配置不一致"，原始 8 字节全存）
- 五源统一事件记录：`{bootSeq, tBootMs, wall?, src, code, data[8], bus}`

**监听集**（硬编码，进头文件常量表）：0x368, 0x346, 0x526, 0x5A5, 0x524（哨兵五源）+ 0x3EE, 0x398（锚）+ 0x2F1, 0x126, 0x356, 0x3C5, 0x396, 0x33A, 0x728（Stage B 指纹族）。共 14 ID，全部 @CanC。

### 5.2 抓拍状态机（`dashAlertWatchPoll` 驱动，帧上下文只置标志）

**severity 门控（Jordan 定案 2026-11-14）**——事件分两类：

| 类 | 触发源 | 动作 |
|---|---|---|
| **CAPTURE 级** | tripwire（0x368 载荷变化）；0x524 任一帧（PM 告警=动力总成级）；0x526/0x5A5 的 a144（配置告警）/a062（跛行）；0x346 上升沿 w062/w063/w064（跛行/优雅关机/扭矩干预） | 记事件 + 自动抓拍 |
| **LOG 级** | 其余全部 a-码与矩阵位（~60 种普通告警） | 只记事件，不开闸 |

理由：开闸=30-60s 全速率串流=beta13 闪烁机制回归（FSD 偏移闪烁/DND 保活抑制窗）。severity 门控让闪烁风险只在车已异常时出现，正常驾驶零影响；普通告警的取证价值由事件日志（码名+数据+时间）承载。

```
IDLE ─事件→ FLUSH ─环回灌毕→ ARMED ─post窗(30s,可延长)→ LOCKING ─锁毕→ COOLDOWN(60s)→ IDLE
规则：
 - 黑盒已在录制（手动武装）：跳过 FLUSH/ARMED，直接计 post 窗后锁定
 - 抓拍进行中再触发：post 窗 +15s（上限 60s，§8④ 裁决），不重复开新会话
 - 自动抓拍会话保留最近 3 个，超出自动 session_delete 最老者（防保护块占满）
 - 回灌：监听集环按时间序 dashRecV2Submit 进黑盒（原始 tsUs 保留），随后实帧自然续写
 - 全程不碰总线模式（CanC 保持 LISTEN_ONLY；与 autoshift/forge 的 wantTx OR 语义无关）
```

### 5.3 持久化

- **事件日志**：NVS 单 blob（键 `alertEvLog`，24×16B=384B 环形重写；bootSeq 计数键 `alertBoot`）。事件稀疏（正常零帧），写寿命无忧
- **抓拍会话**：黑盒分区（既有 session 机制、既有下载端点，零新导出路径）
- **监听集环**：纯 PSRAM，掉电即弃（pre 上下文的持久化由回灌后的锁定会话完成）

### 5.4 WebUI（防护页）

新增"告警取证"卡：
- 状态行：监听 X 帧 / 环占用 / 最近事件时间 / 抓拍状态
- 0x346 当前锁存位图（解码名，最多列 8 个活跃位）
- 事件列表（最近 10 条：时间+源+解码名+数据 hex）
- 总开关（默认**开**——纯被动零风险；关=哨兵停+环停）
- 导出：事件 JSON（GET `/alert_events`）+ 抓拍会话用既有下载按钮

### 5.5 解码表（静态，~1.2KB flash）

- w/a 共享码表 64 条（w062_systemLimpMode 等，DI/DIS 同名）
- PM 专表：a043_configInconsistent（含 GTW_autopilot vs expectedAutopilot 语义注记）等 PM 头部码
- 表条目：`{code, "w062_systemLimpMode"}` 纯数据，无逻辑分支

## 6. 验证策略

- 纯核心 native 测试（新 `test_native_alert_watch` env + pytest 契约）：哨兵上升沿/帧事件/环/状态机迁移/回灌迭代器/debounce
- 台架：`rv2_frame` 串口命令重放 sess_124 的真实告警帧序列（0x526/0x5A5/0x346 置位帧在案），验证端到端：事件入库→自动开闸→锁定→会话可下载→事件 JSON
- 田野：beta 装车静默运行一周，验证零误报（正常驾驶零事件）

## 7. 留给实现的自由度

- 解码表的完整 64 条名单（从字典 JSON 机械生成，无判断）
- 事件列表 UI 的具体排版（防护页既有卡片风格内自由发挥）
- 回灌节奏（staging 背压处理细节：丢帧计 loss badge 亦可，pre 上下文允许有损）

## 8. Builder-check 裁决（2026-11-14 评审并入）

评审四问，三裁定一待定：

**① 0x368 tripwire 必须去抖（裁定：按载荷去重）**。降级日每个 0x368 帧（~10Hz）都永久偏离冻结模板——不去重则 24 条事件日志 2.4 秒被刷满、NVS 以 10Hz 重写、post 窗钉死上限。裁定：**每 distinct 8 字节载荷记一条事件**（载荷入事件记录），保持对任何后续变化的敏感；不重基线（冻结模板永远是参照，镜像再变回也不漏）。日志帧无此问题：sess_124/127 实证 0x526/0x5A5 每码一帧不重发；0x346 为常驻重播但按上升沿语义天然去重。

**③ 0x346 跨自身重启（裁定：每 boot 重新事件化）**。我们重启后首个 0x346 帧会把车端仍锁存的位误判为上升沿。裁定：**接受 re-eventing，事件带 bootSeq 标记**——车锁存到车下电，"boot N 时位 X 在锁存"本身就是取证事实；不 baseline-seed（会漏掉重启间隙内置位的位=真证据丢失）、不 NVS 持久化锁存（复杂度不值）。崩溃循环最坏情形受 3 会话保留界约束。

**④ 保留策略 vs 网格容量（裁定：容量感知驱逐）**。3×64 块 > 144 块网格=写者拒写。裁定：**FLUSH/ARM 前计算需求块数（回灌+post 窗估算）vs 空闲块，驱逐最老自动会话直到放得下；仍放不下→降级为 log-only（事件记录抓拍失败原因）**；post 窗上限从 120s 收紧到 **60s**。

**② 抓拍期间的闪烁机制回归（Jordan 定案：severity 门控）**：自动开闸=全速率三总线串流 30-60s，与 beta13 闪烁案同机制（FSD 偏移显示闪烁/DND 保活被抑制窗）。定案：仅 CAPTURE 级事件开闸（清单见 §5.2），普通告警 log-only——闪烁风险只在车已异常时出现。

## 9. 明确不做（再次声明）

写回/配置恢复不在本产品。它的决策证据（PM_a043 行为）由本产品在降级日自动收集。
